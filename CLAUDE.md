# CLAUDE.md — Упай

Наработки, перенесённые из линейки игр X2 LOTO (референс: `ЧҮКӨ`,
репозиторий `Khan1_2D_Cloud`). Это не готовый код игры «Упай», а
проверенная архитектура и конвенции, которые стоит соблюдать с самого
начала, чтобы не наступать на старые грабли.

---

## 0. Главный принцип (не обсуждается)

**LMS определяет исход билета. Клиент только визуализирует.**

- Реальный денежный результат (`win`, `balance`) всегда приходит от LMS.
- PixiJS/Matter.js (или другой рендер/физика) не должны иметь возможности
  превратить один исход лотереи в другой — физика может отличаться в
  деталях (углы, скорость), но целевой результат раунда выбирается
  ДО того, как рендер начинает анимацию, и не может быть изменён
  визуальным слоем.
- Любая "случайность" в физике/анимации допустима только внутри
  визуального шума, который не меняет `scenario`/`win`.

Если при разработке «Упай» это правило начинает мешать (например,
физика может случайно "не долететь"), решение — доработать логику
подгонки к целевой точке (см. п.4), а не ослаблять принцип.

---

## 1. Технологический стек по умолчанию

- **PixiJS** — рендер сцены.
- **Matter.js** (если нужна физика столкновений) — без гравитации,
  фиксированный шаг физики (обычно 1000/60 мс).
- Чистый **HTML/CSS/JS**, без сборщика — так проще деплоить как статику
  и встраивать в iframe LMS.
- **localStorage** — только некритичные пользовательские настройки
  (звук/музыка вкл-выкл, короткая локальная история последних билетов
  для UI). Никогда не хранить там авторитетный баланс или результат.
- CDN с резервным зеркалом (например jsDelivr основной, unpkg резервный).

---

## 2. Структура файлов (базовый шаблон)

```
config.js              — рантайм/LMS-настройки конкретной инсталляции
lms-adapter.js          — весь обмен с LMS (единственная точка входа)
src/scenario-config.js  — единый источник правды по сценариям/визуал-планам
src/visual-config.js    — вся визуальная тонкая настройка (геометрия, тайминги, физика "фана")
src/i18n.js             — таблица локализации
src/game.js             — рендер, state machine, UI, аудио, автоигра
index.html / styles.css — разметка и стили
assets/                 — спрайты, звуки, музыка
ARCHITECTURE.md         — короткое описание архитектуры (эту же секцию используем как шаблон)
```

Важно: **config.js / scenario-config.js / visual-config.js — три разных
слоя, их нельзя смешивать**:
- `config.js` — то, что относится к LMS/деньгам/окружению (denomination,
  currency, endpoints, mock-режим).
- `scenario-config.js` — маппинг "что вернул LMS (scenario id)" →
  "что показать визуально" (сколько фишек выбито, спецэффект и т.д.) +
  demo-мультипликатор ТОЛЬКО для автономного mock/QA-режима.
- `visual-config.js` — чистая визуальная тонкая настройка, не влияет
  на результат: скорости, дуги полёта, размеры, тайминги эффектов.

## 3. Контракт LMS-адаптера (проверенный паттерн)

`lms-adapter.js` реализует единый интерфейс, независимый от конкретной
игры:

```js
window.X2LMS = {
  getGameSettings,   // язык, валюта, denomination(s), demo/real, баланс
  getBalance,        // если требуется отдельный запрос баланса
  createTicket,      // REAL: покупка билета -> {ticketId, scenario, win, balance, ...}
  createDemoTicket,  // DEMO: локальная симуляция без реальных денег
  emit,              // postMessage наружу в родительский iframe
  getSession
};
```

Ключевые решения, которые стоит унаследовать:

- **Два режима инициализации**: `postMessage` (реальная LMS-обёртка,
  игра запущена в iframe) и `query`/`config` (standalone/QA через
  URL-параметры). Определяется `cfg.initMode`/`isMock`.
- **`?mock=true|false`** в URL явно переопределяет `cfg.mock` из
  конфига — удобно для QA-ссылок без пересборки.
- **`?scenario=`** в URL форсирует конкретный сценарий в mock/demo —
  критично для тестирования каждого исхода вручную.
- Все ответы LMS **нормализуются и валидируются** (`normalizeTicket`,
  `normalizeBalance`) — если сервер прислал не то поле или не то число,
  адаптер бросает типизированную ошибку (`BAD_TICKET_RESPONSE`,
  `BAD_SCENARIO_RESPONSE`, `INSUFFICIENT_FUNDS`, `SESSION_TIMEOUT` и т.д.),
  а не падает молча.
- **Идемпотентность запроса билета** — `requestId`/`Idempotency-Key`,
  чтобы повторный сетевой ретрай не купил билет дважды.
- **REAL-баланс приходит только из `X2_LMS_INIT` и из ответа на покупку
  билета** — отдельного эндпоинта "получить баланс" в проде может не
  быть; закладывать это в архитектуру сразу, не изобретать лишний вызов.
- DEMO — это **отдельная, явно помеченная ветка** (`demo: true` в
  ответе), а не просто "mock с другим счётчиком".

Перед стартом «Упай» нужно уточнить фактический контракт LMS у
оператора (эндпоинты, формат PayTicket, имена полей) — но сама
структура адаптера (валидация, mock/demo/real разделение, идемпотентность)
переносится как есть.

## 4. Сценарии / детерминированная визуализация

- LMS возвращает **числовой `scenario`**, а не сразу "что показывать".
  Маппинг scenario id → визуальный план (сколько объектов выбито, есть
  ли спецбонус и т.п.) держится в отдельном конфиге
  (`X2ChukoScenarioConfig`-подобный модуль), чтобы:
  - `lms-adapter.js` мог проверять валидность id и гонять demo-цикл;
  - `game.js` брал из него только `{ ...visual plan }`, никогда сам не
    решал, что выбито;
  - добавление нового сценария не требовало правок в адаптере/рендере —
    только новую запись в конфиге.
- **Детерминизм по `ticketId + scenario`** — если нужна воспроизводимость
  (повтор анимации того же билета даёт тот же визуал), сидировать генератор
  случайных чисел этой комбинацией.
- Денежный `win` **никогда не пересчитывается** из scenario на клиенте в
  REAL-режиме — только в мок/демо для QA.

## 5. UI/визуал независимы от логики

- Фон страницы, ассет поля/сцены, спрайты фигур и тема UI должны быть
  заменяемы независимо от LMS-логики и физики. Не завязывать
  геометрию/хитбоксы на конкретную картинку фона.
- Разделение слоёв рендера (пример из ЧҮКӨ, переносимо почти 1:1):
  1. `bg-layer` — фон страницы (HTML/CSS)
  2. Pixi `fieldLayer` — игровое поле
  3. Pixi `pieceLayer` — игровые объекты
  4. Pixi `outLayer` — объекты, выбывшие из игры/поля
  5. Pixi `fxLayer` — партиклы, вспышки, салют
  6. `ui-layer` — весь HTML-интерфейс поверх Pixi

## 6. Локализация (i18n)

Паттерн — **таблица, не вложенные объекты по языкам**:

```js
const TABLE = [
  { key:'newGame', RU:'Новая игра', EN:'New game', KG:'...', ... },
  ...
];
```

- Один ключ = одна строка сразу со всеми языками — проще добавлять язык
  (новая колонка) и проще видеть, где перевод забыт.
- Отсутствующая колонка для конкретного языка **падает на RU** по
  умолчанию, а не на пустую строку — интерфейс не должен ломаться из-за
  недостающего перевода.
- Имена собственные (названия игры/персонажей) на не-RU/KG языках нужно
  сверять с носителем/оператором перед реальным запуском — транслит "на
  глаз" не финальный вариант.

## 7. Аудио

- Полностью на **Web Audio API** + `<audio>` для файловых треков,
  изолировано от игровой/физической логики: рендер стейта (`renderState`)
  только "слушает" переходы состояний для проигрывания SFX, ни одна
  физическая функция не должна зависеть от аудио.
- Настройки звука/музыки — в `localStorage`, отдельные ключи под sound и
  music.
- Полезные паттерны из ЧҮКӨ:
  - процедурные UI-тоны через осцилляторы (клик, бросок, удар, результат)
    как fallback/основной SFX без необходимости грузить файлы;
  - опциональные файловые SFX (`soundFiles: {throw, impact, win, ...}`) с
    отдельной громкостью;
  - фоновая музыка — плейлист треков со случайным порядком без повторов
    подряд;
  - редкие голосовые "теги" (voice barks) со своим таймером и
    приглушением музыки (`duckFactor`) на время воспроизведения;
  - обязательно try/catch вокруг чтения/записи localStorage — приватные
    окна/заблокированное хранилище не должны валить игру.

## 8. Автоигра (если у «Упай» тоже будет)

Проверенная state-machine:

- Пользователь сначала **выбирает количество** (кнопки из
  `autoPlayCounts`), фактический запуск — отдельным подтверждающим
  действием ("Старт N"), а не сразу по выбору числа.
- Автоигра **дожидается полного визуального celebration-эффекта**
  текущего раунда (конфетти/фейерверк и т.д.) прежде чем начать
  следующий — иначе выигрышный эффект обрезается, и это плохо
  воспринимается игроком. Длительность паузы вычисляется из реальных
  таймингов эффектов, а не захардкожена.
- "Стоп" во время автоигры не прерывает уже купленный/играющийся раунд —
  докручивает текущий билет до конца и останавливается на границе
  раунда.
- Между покупкой билета и стартом броска — небольшая фиксированная
  задержка (`autoPlayThrowDelayMs`), чтобы даже в автоигре был читаемый
  ритм, а не мгновенный "телепорт" в анимацию.

## 9. Ошибки, которые уже находили и чинили (не повторять)

- Не завязывать масштаб/размер игровых предметов и дальность разлёта на
  конкретный фон-картинку "на глаз" — при смене ассета всё "плавает".
  Дальность/зоны считать от геометрии поля (`innerRadius`,
  `maskRadiusX/Y`), не от пикселей конкретного скриншота.
- Не раскрывать результат LMS (`win`, множитель) до того, как визуальный
  раунд реально "settled" — иначе игрок видит исход раньше, чем
  заканчивается анимация броска.
- Не считать локальную историю билетов в `localStorage` авторитетной —
  это только UX-удобство ("последние билеты"), полная история — в
  личном кабинете LMS. Хранить в ней минимум полей (`ticketId`, `win`),
  ограниченное количество записей, отдельные ключи для REAL/DEMO.
- Не смешивать mock-режим (standalone GitHub-демо без LMS вообще) и
  demo-режим (внутри реальной LMS-обёртки, но без реальных денег) — это
  разные вещи с разной логикой инициализации.

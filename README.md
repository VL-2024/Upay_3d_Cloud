# УПАЙ — 3D-прототип

Интерактивный прототип моментальной электронной лотереи «УПАЙ» (X2 LOTO),
визуально и механически основанной на традиционной кыргызской игре в чүкө.
Реализовано на [Babylon.js](https://www.babylonjs.com/) +
[Havok Physics](https://www.havok.com/).

Полное описание идеи, правил и требований — в
`docs/UPAY_Game_Concept_Rules_Technical_Spec_v1.0.docx` (актуальный документ;
исходный физический ТЗ v0.1 сохранён в
`docs/UPAY_v0.1_Technical_Specification.docx` для истории). Контракт
интеграции с LMS — в `docs/LMS_API.md`, он идентичен остальным играм
семейства (см. `VL-2024/Altyn-Khan-KG@modern-3d`): тот же `lms-adapter.js`
файл, тот же postMessage/PayTicket протокол — отличается только каталог
сценариев (`src/scenario-catalog.js`) и сама игровая логика.

## Текущий статус

Реализован полный игровой цикл билета — от запроса у LMS-адаптера до показа
итога — включая все 8 кодов сценария:

- физика чүкө, рассыпание, стабилизация, классификация 4 положений;
- валидатор раскладки с невидимым reroll и гарантией прохождения сценария
  (в т.ч. резервирование чүкө под ход на Хана);
- выбор пары (tap-to-target и swipe) и управляемый щелчок;
- сбор в зоны УПАЙ 1/2 с дуговой анимацией переноса;
- сценарный движок `ZERO_A / ZERO_B / ONE / ONE_PLUS / TWO / KHAN / TWO_KHAN / ALTYN`;
- Хан: резервирование, разблокировка, сообщение «ЕЩЁ ОДИН ХОД» для TWO_KHAN;
- LMS-интеграция (`window.X2LMS`) — тот же адаптер/контракт, что и в
  остальных играх семейства (postMessage init/session, PayTicket, DEMO-режим,
  коды ошибок) — см. `docs/LMS_API.md`.

**Вне текущего объёма** (см. §24 полного ТЗ): финальные 3D-модели и арт,
звук, production UI/VFX, подключение реального LMS, мобильная
сертификация. Debug-инструменты (подписи положений, FPS, wireframe)
остаются в клиенте по прямому указанию ТЗ (§13 — допустимы на этапе
разработки).

## Запуск

Требуется Node.js 18+.

```bash
npm install
npm run dev      # dev-сервер (Vite) с горячей перезагрузкой
```

Откройте адрес, который выведет Vite (обычно `http://localhost:5173`).
Интерфейс mobile-first: лучше всего смотрится в вертикальной ориентации
на узком экране (эмулятор телефона в DevTools или реальное мобильное
устройство в локальной сети через `--host`).

```bash
npm run build     # production-сборка в dist/
npm run preview   # локальный просмотр production-сборки
```

Открывать `index.html` напрямую двойным кликом (`file://`) нельзя — браузер
блокирует ES-модули по CORS. Если это произошло, клиент сам покажет
подсказку вместо бесконечной загрузки.

Havok физика загружается как WASM через `@babylonjs/havok`; интернет не
нужен после `npm install` — всё собирается локально через Vite.

### GitHub Pages

Собранная версия публикуется в отдельную ветку `gh-pages` (только
статический билд, не исходники — так настроен GitHub Pages в этом
репозитории). Обновить после изменений:

```bash
npm run build
# скопировать содержимое dist/ в корень ветки gh-pages и запушить
```

## Управление

- Кнопка **«НОВЫЙ БИЛЕТ»** запрашивает билет через `window.X2LMS`
  (`createDemoTicket`/`createTicket` в зависимости от режима) и запускает
  рассыпание.
- **Tap-to-target**: тап по чүкө делает его источником, допустимые цели
  (то же положение, включая Хана после разблокировки) подсвечиваются
  зелёным — тап по цели выполняет щелчок.
- **Swipe**: проведите пальцем/мышью от чүкө в сторону цели — направление
  свайпа сопоставляется с проекциями допустимых целей на экран.
- Целевой чүкө после успешного хода дугой переносится в зону УПАЙ 1/2;
  чүкө-источник возвращается в игру на новом положении.
- Выпадающий список **«Сценарий»** — QA-инструмент: `авто` циклически
  перебирает все 8 кодов, либо можно закрепить конкретный код через
  `?scenario=CODE` в адресной строке (§18 ТЗ; тот же механизм, что и в
  остальных играх семейства — смена значения перезагружает страницу).
- Чекбоксы внизу — debug-режимы: FPS, подписи положений над чүкө,
  wireframe вместо физических тел.

## Структура проекта

```
index.html               Контейнер приложения, canvas, HUD-разметка
public/lms-config.js      window.X2_GAME_CONFIG — тот же формат во всех играх семейства
public/lms-adapter.js      window.X2LMS — адаптер, файл идентичен другим играм (не менять!)
public/src/scenario-catalog.js  window.X2ChukoScenarioConfig — коды сценария УПАЙ (единственное,
                                 что в LMS-контракте отличается между играми)
src/main.js               Bootstrap: Engine, сцена, физика, билетный цикл через window.X2LMS, UI
src/scene.js               Камера, свет, поле, невидимые физические границы
src/physics.js              Havok: инициализация, rigid body, sleep/stability
src/chuko.js                 Процедурная модель обычного чүкө + hitProxy + физика
src/khan.js                   Хан: isKhan=true, khanUnlocked
src/scatter.js                 Рассыпание: позиции/высоты/вращения/импульсы
src/orientation.js              Классификация AYKUR/TAA/CHIK/BOK
src/layout-validator.js          Проверка раскладки + гарантия прохождения
                                  сценария (резерв чүкө под Хан) + условия reroll
src/pair-selector.js              Выбор source/target, подсветка
src/input.js                       Tap/swipe → pointer events → flick
src/flick.js                        Импульс щелчка + коррекция траектории в полёте
src/collector.js                     Зоны УПАЙ 1/2: слоты, дуговой перенос
src/scenario-engine.js                Все 8 кодов сценария, шаги pair/khan
src/game-state.js                     Полная машина состояний партии
src/config.js                          Игровые параметры, НЕ LMS-контракт (см. ниже)
assets/models/, assets/textures/        Заготовки под будущие ассеты (пока пусто)
docs/                                    Технические задания + LMS_API.md
```

`public/` копируется Vite в сборку как есть (без бандлинга/фингерпринтинга)
— это принципиально для `lms-adapter.js`: файл должен оставаться
byte-identical между играми, а не превращаться в захэшированный чанк.

## Модель чүкө (временная геометрия)

Финальных 3D-моделей ещё нет (см. §24 ТЗ — «Заменить технические модели
финальными 3D-ассетами» — отдельный будущий этап). Чтобы физически повторить
поведение настоящей астрагалы (4 устойчивых положения, а не 6 как у куба),
чүкө строится процедурно (`src/chuko.js`) как прямоугольный блок,
вытянутый по локальной оси X, со скруглёнными полусферическими торцами
(через `CSG.union`). У такой формы ровно 4 плоские устойчивые грани
(±Y, ±Z) — скруглённые концы не дают устойчиво «встать на попа».
`src/orientation.js` классифицирует положение, сравнивая мировую ось Y с
этими четырьмя локальными нормалями.

Видимая геометрия мала на экране (особенно на телефоне), поэтому у
каждого чүкө есть невидимый (но пикающийся, `alpha=0`) `hitProxy` —
дочерняя сфера увеличенного диаметра для надёжного tap/swipe-попадания;
сам видимый меш `isPickable = false`.

## Сценарный движок и детерминированность (§7 ТЗ)

`scenario-engine.js` хранит билет как фиксированную последовательность
шагов `'pair'`/`'khan'` — какую именно пару выбрать и в каком порядке,
решает игрок, но число и тип шагов заданы кодом сценария и не меняются.
`ticket.scenarioKey`, пришедший от `window.X2LMS.createDemoTicket()` /
`createTicket()`, передаётся прямо в `ScenarioEngine.start()` — ключи
каталога (`src/scenario-catalog.js`) выбраны совпадающими с кодами
`scenario-engine.js`, трансляция не нужна. DEMO не считает выигрыш из
`Math.random()` (§18, §21) — только `demoMultiplier × denomination` из
каталога; в REAL-режиме `win`/`balance` целиком приходят от LMS, тот же
адаптер меняет только `mock:false` в `lms-config.js`, без правок
gameplay-кода.

Чтобы раскладка гарантированно позволяла пройти Хан-шаг, `layout-validator.js`
после классификации проверяет, что среди обычных чүкө есть хотя бы один с
положением Хана — иначе reroll. Найденный чүкө резервируется
(`main.js` ставит ему `state = 'reserved'`) и не предлагается игроку как
source/target до момента разблокировки Хана — иначе игрок мог бы случайно
собрать именно эту пару раньше времени и сорвать Хан-шаг.

## config.js — параметры

Все числовые параметры вынесены в `src/config.js`, логику менять не нужно,
чтобы подстроить баланс/физику/UI:

- `chukoCount`, `chukoScale`, `khanScale`, `chukoSize` (включая `hitProxyDiameter`)
- `physics` — масса, friction, restitution, linear/angular damping, гравитация
- `workArea` — размер игровой зоны и высота невидимых границ
- `ui.bottomReservedFraction` — доля экрана снизу под UI (камера туда не рендерится)
- `scatter` — радиус/высота/джиттер/импульс рассыпания
- `stability` — пороги скорости и число кадров для признания «уснувшим»
- `layoutValidator` — допуски валидатора раскладки и лимит попыток reroll
- `flick` — сила щелчка, коррекция траектории, вариативность вращения
- `highlight` — цвета/интенсивность подсветки source/target
- `input` — пороги свайпа (дистанция/время/направление)
- `scenario.pairsPerUpay` — сколько пар в одном Упай (игровое правило,
  не LMS-контракт — DEMO-выплаты и коды сценария живут в
  `public/src/scenario-catalog.js`, см. `docs/LMS_API.md`)
- `collector` — позиции зон УПАЙ 1/2, шаг между слотами, параметры дуги переноса
- `debug` — FPS, физ. тела, подписи положений, траектория

## Правила тестирования

Формальных автотестов нет. Ручная проверка перед коммитом/демо:

1. `npm run dev`, открыть в мобильном viewport (вертикальная ориентация).
2. «НОВЫЙ БИЛЕТ» несколько раз подряд (режим «авто») — раскладка каждый раз
   стабилизируется и валидируется без бесконечных reroll (в консоли
   предупреждение — сигнал, что параметры валидатора/камеры разошлись с
   физикой, чинить в `config.js`).
3. Включить debug-подписи положений — классификация AYKUR/TAA/CHIK/BOK не
   «дёргается» на уснувших объектах.
4. Source/target: допустимые цели подсвечиваются зелёным; тап по
   недопустимой цели/пустому месту снимает выбор без штрафа; целевой чүкө
   дугой улетает в зону УПАЙ, источник остаётся в игре.
5. Прогнать через QA-селектор каждый из 8 кодов до конца (включая ход на
   Хана для KHAN/TWO_KHAN/ALTYN) — убедиться, что итоговая надпись и
   DEMO-сумма соответствуют коду, а Хан недоступен до разблокировки.
6. Проверить FPS на целевом устройстве/эмуляторе — просадки диагностировать
   до работы над визуальными эффектами.

При правке физических параметров (`physics`, `scatter`, `stability`)
после каждого изменения повторяйте шаги 2–3: нестабильные damping/friction
проявляются как «дрожащие» или не засыпающие объекты.
